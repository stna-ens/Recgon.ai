# Phase 3.6 Plan 01: Walking Skeleton Summary

**Schema + cron route + type scaffolding for graduated overdue-task pressure.**

## What shipped

1. **Migration** `supabase/migrations/20260519_overdue_pressure_schema.sql`:
   - `agent_tasks.overdue_tier int not null default 0`
   - `agent_tasks.last_overdue_action_at timestamptz`
   - `teams.overdue_pressure_enabled boolean not null default true`
   - Extends `teammate_event_log_event_check` with `nudged`, `escalated`, `auto_rescheduled`, `snoozed`
   - Partial index `idx_agent_tasks_overdue_sweep` on `(team_id, scheduled_date)` covering the sweep's hot path (active-status rows with non-null `scheduled_date`)

2. **Cron route** `src/app/api/cron/overdue-sweep/route.ts`:
   - GET/POST handler mirroring `/api/cron/llm-jobs` shape
   - `CRON_SECRET` bearer auth enforced in production, skipped in local dev
   - Returns `{ ok, teamsProcessed, actionsByKind, durationMs }`

3. **vercel.json**: added daily cron schedule `0 9 * * *` for `/api/cron/overdue-sweep` and a `maxDuration: 60` function entry.

4. **Type scaffolding** in `src/lib/recgon/types.ts`:
   - `OverdueTier = 0 | 1 | 2 | 3`
   - `OverdueAction` discriminated union (`nudge_teammate` / `escalate_to_owner` / `auto_reschedule` / `none`)
   - `OverdueSweepCounts` — counter shape returned by the sweep

5. **Stub function** `sweepOverdueTeams()` in `src/lib/recgon/storage.ts` — returns zeros. Plan 02 replaces with the real policy loop.

## Plain-English summary

Today Recgon does nothing when a task's deadline passes. This plan lays the *plumbing* so the daily cron is on the schedule, the database has somewhere to record what action it took, and the types are pinned. Nothing user-visible changes yet. Plan 02 will write the decision rules; Plan 03 will send the emails; Plan 04 will add the red chip and snooze button.

## Deviations from Plan

- **Migration apply step deferred.** The plan specified applying the migration via `mcp__supabase__apply_migration` to project `hrgyrtgpgvsgvxmozcax`, but the Supabase MCP tool is not exposed in this executor agent's tool surface. The migration file is committed and ready; the user (or a Claude Code session with the Supabase MCP attached) must apply it manually before Plan 02 lands. Per CLAUDE.md user-role rule (no CLI commands offered), I'm calling this out plainly: the bookkeeping fields don't exist in Supabase yet — the SQL file does.
- **`actionsByKind` instead of `actions`.** The plan's "must_haves" snippet said `{ teamsProcessed: 0, actions: 0 }`, but the body of the plan (and the policy's discriminated union) needed per-kind counters so Plan 04's owner-board can show `nudged: 3, escalated: 1` etc. without re-querying. Shipped the richer `actionsByKind` shape — additive, no API contract was committed elsewhere yet.
