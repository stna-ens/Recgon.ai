# Phase 3.6 / Plan 04 — Overdue Task Pressure: UI Surfacing

Closed the loop on the dispatcher's new pressure behavior. Every place a task is rendered now shows a red/pink chip when it slips; the team owner sees tier-encoded escalation color (pink → amber → red filled); the owner-only snooze control reschedules in one click; and the daily cron now emits structured `overdue_counter` log lines so policy fire-rate is visible without log spelunking.

## What landed

**New component — `src/components/v2/calendar/OverdueChip.tsx`** (101 lines)
- `<OverdueChip tier={0..3} days={N} ownerView={bool} />` — pure presentation. Caller is responsible for gating on `isOverdue(task, today)`; the chip itself just renders.
- Tier color encoding (owner view): tier 0/1 → `var(--signature)` outline (pink), tier 2 → `var(--warning)` outline (amber), tier 3 → `var(--danger)` filled (red, white text).
- Assignee view: uniform pink outline regardless of tier — the assignee never sees that the owner has been escalated to (mirrors Phase 1 D-20 privacy rule, locked in CONTEXT.md).
- Label: `"1 day late"` (singular) / `"N days late"` (plural). Mono font + tracking matches `recgon-label` vocabulary. No emojis.
- No new design tokens — uses existing `var(--signature)`, `var(--warning)`, `var(--danger)`.

**Updated — `src/components/v2/calendar/EventChip.tsx`**
- New `ownerView?: boolean` prop (default `false`).
- Derives `isOverdue` + `daysOverdue` via the pure `overduePolicy` helpers; renders `<OverdueChip>` between the team-badge row and the reschedule-request flag.
- Adds `.cal-chip-overdue` placement style for both single-day and multi-day chip variants.

**Updated — `src/components/v2/calendar/SwimLane.tsx`**

**Updated — `src/components/v2/calendar/TaskDetailPanel.tsx`**

## Key behaviors verified

- **Tier color encoding (owner view):** asserted by `chip.style.borderColor` / `chip.style.background` / `chip.style.color` for tiers 0, 1, 2, 3.
- **Assignee privacy:** for ALL four tiers, `ownerView={false}` produces an identical signature-pink outline chip — escalation status never leaks to the assignee.
- **Render gate:** `isOverdue` returns false for null-date, future-date, and terminal-status tasks; returns true for active + past-date.
- **Snooze owner-only:** TaskDetailPanel does not render the SNOOZE section when `isOwner={false}`, even on overdue tasks. Hidden also for owner viewing a non-overdue task.
- **Snooze POST contract:** clicking "3 days" fires exactly `POST /api/teams/{teamId}/tasks/{taskId}/snooze` with body `{"days":3}`. URL is built from the real `task.teamId` + `task.id`.
- **Counter wiring:** runner emits one `logOverdueCounter` per successful action across all 4 paths (tier 1, tier 2, tier 3 with capacity, tier 3 handoff). Snooze route emits on success after `snoozeTask`.

## Deviations from plan

- **PersonalCalendar `ownerView`:** plan implied this could surface owner badges; I left it at the default `false`. Personal calendar aggregates across teams — "ownership" is per-team, not per-view. Rule 2 (correctness): showing the team-owner tier color on a viewer's personal-view list of cross-team tasks would leak escalation status from teams where they aren't owner. Decision aligns with CONTEXT.md "Owner-only escalation visibility" — only the team-scoped WeekCalendar passes the owner flag.
- **OverdueChip path:** plan suggested putting the chip directly in `TaskCard.tsx`. There is no `TaskCard.tsx` in the codebase — the equivalent surfaces are `EventChip.tsx` (calendar) + the inline article rendered by `/tasks/page.tsx`. Created a standalone `OverdueChip.tsx` so both consumers share it. Rule 3 (blocking issue): no `TaskCard.tsx` to write into.
- **AgentTask type extension:** the plan said "verify and add the camelCase mapping if missing". Added `overdueTier` + `lastOverdueActionAt` as **optional + nullable** to `AgentTask` (additive — back-compat preserved for pre-Plan-01 rows and test fixtures). Rule 2: required so the UI can read tier without a second query.
- **Inbox API fallback ladder:** plan didn't call out the API, but the new `overdue_tier` / `last_overdue_action_at` columns aren't guaranteed in every environment. Added a three-tier `select` fallback (reschedule + overdue → reschedule only → legacy) so the migration sequencing doesn't break the inbox. Rule 2.

No CLAUDE.md violations. No security issues. No new env vars. No architectural changes.
