## Goal

Quoted from `.planning/ROADMAP.md §Phase 3.5`:

> A team owner opens a single page and immediately understands the team's task picture: who is doing what, when each task is scheduled, why each assignee was picked, and which tasks are flagged for triage or deferred. The page replaces the long list view with a dense, scannable grid — Excel-table feel, not literal spreadsheet. Triage + deferred items (from Phase 3 dispatcher) are first-class columns/rows, not buried in detail pages.

**Primary recommendation:** Install `@dnd-kit/core@6.3.1` (stable, NOT the v0.4 alpha). Wrap a new owner-only `OwnerWorkloadBoard` client component (rendered as branch of `/projects/page.tsx` when `currentTeam.role === 'owner'`) in a single `DndContext`. Reuse `SwimLane` + `EventChip` + `TaskDetailPanel` verbatim — but REPLACE the existing HTML5 `onDragStart`/`onDrop` wiring with dnd-kit `useDraggable` + `useDroppable` so we get keyboard accessibility and touch sensors for free. Introduce `POST /api/recgon/tasks/[id]/reschedule` (owner-only, body `{ scheduledDate: string | null }`) wrapping existing `deferTaskScheduledDate()`. Optimistic-update on drop, revert + toast on API failure. Same role-guard pattern as `/projects/[id]/tasks/page.tsx` (client-side via `useTeam()`).

## dnd-kit Patterns for 2D Grid

**Conceptual model:** Each `EventChip` is a `useDraggable`. Each day-cell inside `SwimLane` is a `useDroppable`. Each dock row is also a `useDraggable` (drag dock-item onto cell). `DndContext` wraps the whole owner board page.

### Pattern 1: Single DndContext at page root with sensors + a11y

```tsx
// Source: dndkit.com/api-documentation (legacy v6 API)
'use client';
import {
  DndContext,
  closestCenter,
  PointerSensor,
  KeyboardSensor,
  useSensor,
  useSensors,
  type DragEndEvent,
} from '@dnd-kit/core';

export function OwnerWorkloadBoard() {
  // 5px activation distance prevents accidental drags on click.
  // Built-in KeyboardSensor handles Space=pick, Arrow=move, Enter=drop, Esc=cancel.
  const sensors = useSensors(
    useSensor(PointerSensor, { activationConstraint: { distance: 5 } }),
    useSensor(KeyboardSensor),
  );

  function onDragEnd(event: DragEndEvent) {
    const { active, over } = event;
    if (!over) return;
    // active.id = task id. over.id = encoded "<teammateId>__<dateISO>" or "dock"
    handleDrop({ taskId: String(active.id), dropTargetId: String(over.id) });
  }

  return (
    <DndContext
      sensors={sensors}
      collisionDetection={closestCenter}
      onDragEnd={onDragEnd}
      // dnd-kit's accessibility plugin auto-injects screen-reader announcements.
      // Customize for owner board domain language:
      accessibility={{
        announcements: {
          onDragStart: ({ active }) => `Picked up task ${active.id}.`,
          onDragOver: ({ active, over }) =>
            over ? `Task ${active.id} is over ${over.id}.` : `Task ${active.id} is no longer over a target.`,
          onDragEnd: ({ active, over }) =>
            over ? `Task ${active.id} dropped on ${over.id}.` : `Task ${active.id} drop cancelled.`,
        },
      }}
    >
      <TriageDock />
      <WorkloadGrid />
    </DndContext>
  );
}
```

### Pattern 2: Draggable chip + droppable cell

```tsx
// Source: dndkit.com/api-documentation/draggable/usedraggable
import { useDraggable, useDroppable } from '@dnd-kit/core';
import { CSS } from '@dnd-kit/utilities';

function DraggableChip({ task }: { task: AgentTask }) {
  const { attributes, listeners, setNodeRef, transform, isDragging } = useDraggable({
    id: task.id,
    data: { kind: 'task', task },
  });

  const style = {
    transform: CSS.Transform.toString(transform),
    opacity: isDragging ? 0.5 : 1,
  };

  return (
    <div ref={setNodeRef} style={style} {...listeners} {...attributes}>
      <EventChip card={toCalendarCard(task)} onClick={openDetail} />
    </div>
  );
}

function DroppableCell({ teammateId, dateISO, children }) {
  const { isOver, setNodeRef } = useDroppable({
    id: `${teammateId}__${dateISO}`,
    data: { kind: 'cell', teammateId, dateISO },
  });
  return (
    <div ref={setNodeRef} className={`cal-day-cell${isOver ? ' is-drop-hover' : ''}`}>
      {children}
    </div>
  );
}
```

**Wrapper strategy:** wrap each `EventChip` in `<DraggableChip>` from the OUTSIDE. Don't modify `EventChip.tsx` internals. The existing HTML5 drag listeners (`draggable`, `onDragStart`, `onDragEnd`) on `EventChip` should be DISABLED in owner-board mode (pass `draggable={false}` prop). The existing `SwimLane.tsx` HTML5 drop wiring (`onDragOver`/`onDrop`) should also be disabled in owner-board mode (e.g., introduce a `dragMode: 'native' | 'dnd-kit'` prop, default `native` to preserve current `/calendar` behavior, set to `dnd-kit` from the new owner board).

### Pattern 3: Optimistic update + API rollback

```tsx
// Mirrors src/app/tasks/page.tsx optimistic pattern (Recgon convention).
const [optimisticOverrides, setOptimisticOverrides] = useState<Record<string, Partial<AgentTask>>>({});

async function handleDrop({ taskId, dropTargetId }) {
  const target = parseDropTarget(dropTargetId); // { teammateId, dateISO } or 'dock'
  if (!target) return;

  const original = tasks.find(t => t.id === taskId);
  if (!original) return;

  const optimistic = {
    ...(target.teammateId !== original.assigneeId ? { assigneeId: target.teammateId } : {}),
    ...(target.dateISO !== original.scheduledDate ? { scheduledDate: target.dateISO } : {}),
  };
  setOptimisticOverrides(prev => ({ ...prev, [taskId]: optimistic }));

  try {
    if ('assigneeId' in optimistic) {
      const res = await fetch(`/api/recgon/tasks/${taskId}/assign`, {
        method: 'POST',
        body: JSON.stringify({ assigneeId: optimistic.assigneeId }),
      });
      if (!res.ok) throw new Error((await res.json()).error);
    }
    if ('scheduledDate' in optimistic) {
      const res = await fetch(`/api/recgon/tasks/${taskId}/reschedule`, {
        method: 'POST',
        body: JSON.stringify({ scheduledDate: optimistic.scheduledDate }),
      });
      if (!res.ok) throw new Error((await res.json()).error);
    }
    addToast('updated', 'success');
    refresh();
  } catch (err) {
    // Rollback: drop the optimistic override; the next render uses real data.
    setOptimisticOverrides(prev => { const next = { ...prev }; delete next[taskId]; return next; });
    addToast(err instanceof Error ? err.message : 'failed', 'error');
  }
}
```

**Convention note:** `src/app/tasks/page.tsx` uses an `optimistic` map keyed by `taskId → ColumnKey`. The owner board generalizes this to `taskId → Partial<AgentTask>` because drag-drop changes EITHER assignee OR scheduledDate OR both (dock-onto-cell). This is additive, not a regression of the existing pattern.

### Pattern 4: Touch fallback + accessibility

`PointerSensor` already covers mouse + touch + pen via Pointer Events spec. No need for separate `TouchSensor` unless we want different activation constraints per input. The 5px activation distance prevents accidental drags on touch tap. [CITED: dndkit.com/extend/sensors]

`KeyboardSensor` is the a11y win — included in default sensors. Built-in keyboard codes:
- `Space` / `Enter` → pick up / drop
- `ArrowUp/Down/Left/Right` → move
- `Escape` → cancel

For a 2D grid, the default `coordinateGetter` (linear) is fine — focus moves to the next droppable in DOM order. We do NOT need `sortableKeyboardCoordinates` (that's for `@dnd-kit/sortable` 1D lists).

### Anti-Patterns to Avoid

- **Don't put `DndContext` inside the dock OR inside each lane.** One context per page, at the root of `OwnerWorkloadBoard`. Otherwise drag-from-dock-onto-cell breaks.
- **Don't use `useSortable`.** `@dnd-kit/sortable` is for reorderable lists. The owner board is positional, not ordered. Keep dependencies minimal.
- **Don't keep the existing HTML5 drag wiring active alongside dnd-kit.** Both will fire and create double drops. Add a `dragMode` prop to `SwimLane` / `EventChip`.
- **Don't update `agent_tasks` directly from the client.** Always go through API endpoint with `verifyTeamAccess` owner check.

## New Endpoint Design — POST /api/recgon/tasks/[id]/reschedule

**Path:** `src/app/api/recgon/tasks/[id]/reschedule/route.ts`
**Method:** `POST`
**Auth:** Owner-only (mirror `/assign`).
**Body:** `{ scheduledDate: string | null }` where `scheduledDate` is ISO date `YYYY-MM-DD`. `null` means "unschedule" (clear `scheduled_date`).

**Why POST not PATCH:** Existing manual-assign endpoint is POST. Stay consistent with the route family. PATCH on the parent `/route.ts` would force adding selective field updates; cleaner to keep one verb-per-route.

**Implementation sketch:**

```ts
// src/app/api/recgon/tasks/[id]/reschedule/route.ts
import { NextResponse } from 'next/server';
import { auth } from '@/auth';
import { getTask, deferTaskScheduledDate, logEvent } from '@/lib/recgon/storage';
import { verifyTeamAccess } from '@/lib/teamStorage';

export async function POST(
  request: Request,
  { params }: { params: Promise<{ id: string }> },
) {
  const { id: taskId } = await params;

  const session = await auth();
  if (!session?.user?.id) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

  const task = await getTask(taskId);
  if (!task) return NextResponse.json({ error: 'Not found' }, { status: 404 });

  const role = await verifyTeamAccess(task.teamId, session.user.id);
  if (role !== 'owner') return NextResponse.json({ error: 'Access denied' }, { status: 403 });

  let body: unknown;
  try { body = await request.json(); } catch { return NextResponse.json({ error: 'Invalid JSON body' }, { status: 400 }); }
  const scheduledDate = body && typeof body === 'object' && 'scheduledDate' in body
    ? (body as { scheduledDate: unknown }).scheduledDate
    : undefined;
  // Allow null (unschedule) or YYYY-MM-DD string. Reject anything else.
  if (scheduledDate !== null && (typeof scheduledDate !== 'string' || !/^\d{4}-\d{2}-\d{2}$/.test(scheduledDate))) {
    return NextResponse.json({ error: 'scheduledDate must be YYYY-MM-DD or null' }, { status: 400 });
  }

  // deferTaskScheduledDate exists in storage.ts (used by dispatcher Phase 3).
  // For owner-driven reschedule the schedule_note copy should differ — pass through a variant.
  // Planner: decide whether to extend deferTaskScheduledDate signature or add ownerRescheduleTask().
  // Recommendation: add ownerRescheduleTask(taskId, newDate | null, ownerId) to keep audit copy honest.
  await ownerRescheduleTask(taskId, scheduledDate, session.user.id);

  await logEvent({
    teamId: task.teamId,
    teammateId: task.assigneeId,
    taskId,
    event: 'owner_rescheduled',
    payload: {
      owner_user_id: session.user.id,
      prior_scheduled_date: task.scheduledDate ?? null,
      new_scheduled_date: scheduledDate,
    },
  });

  return NextResponse.json({ ok: true, taskId, scheduledDate });
}
```

**Idempotency:** Writing the same date is a safe no-op overwrite (matches existing `deferTaskScheduledDate` semantics — see `src/lib/recgon/storage.ts:638-653`). Multiple drag-drops in flight resolve to last-write-wins per CONTEXT D-deferred (multi-owner conflict).

**Audit invariant:** Every reschedule produces an `agent_events` row with `event: 'owner_rescheduled'`. This is the trail for "who moved this task" if the assignee asks.

**State-machine constraint:** Unlike `/assign`, reschedule should work on tasks in `unassigned`, `assigned`, `accepted`, and `in_progress` states. A completed task should NOT be reschedulable (return 409). Planner: add a state-allowlist check at the top of the handler.

## Triage Dock Data Query

The dock shows two distinct row kinds (D-12 + D-13):

```sql
-- Triaged tasks (no calendar slot, ONLY in dock):
SELECT * FROM agent_tasks
WHERE team_id = $1
  AND status = 'unassigned'
  AND triage_note IS NOT NULL
  AND (scheduled_date IS NULL OR scheduled_date <= CURRENT_DATE);

-- Deferred tasks (in dock AS REVIEW + in calendar at future date):
SELECT * FROM agent_tasks
WHERE team_id = $1
  AND status = 'unassigned'
  AND triage_note IS NULL
  AND scheduled_date > CURRENT_DATE;
```

**API surface recommendation:** Add `GET /api/recgon/owner/dock?teamId=X` returning `{ triaged: AgentTask[], deferred: AgentTask[] }`. Keep separate from `/api/inbox` (which is personal-scoped). Owner-only via `verifyTeamAccess`.

**Per-user dismissal persistence (D-17):** Two options for the planner:
- (A) New table `owner_dock_dismissals(user_id, task_id, dismissed_at)` — clean, queryable.
- (B) Reuse `agent_events` with `event: 'owner_dismissed_deferral'` filtered per-user — no new table but query is heavier.

Recommendation: (A). The per-user dismiss is a UX feature, not an audit event. Keep `agent_events` for state-mutating actions only.

## Common Pitfalls

### Pitfall 1: React hook order violation in /projects/page.tsx refactor
**What goes wrong:** Adding `if (currentTeam.role === 'owner') return <OwnerBoard />` BEFORE the existing useState/useEffect/useCallback calls.
**Why it happens:** Owner-board branch tempts you to early-return; the existing tile-list logic (with all its hooks) only matters for non-owner.
**How to avoid:** Either (a) keep all hooks at the top, branch in render only; or (b) extract the existing tile-list code into a separate `<NonOwnerProjectsView />` component that owns its own hooks, and have `page.tsx` be a thin role router.
**Warning sign:** Console error "Rendered fewer hooks than expected" or "Hooks called in different order".

### Pitfall 2: Both HTML5 and dnd-kit drag handlers active
**What goes wrong:** Existing `SwimLane.tsx` (used by `/calendar`) has HTML5 `onDragOver`/`onDrop` wired. If we wrap chips in dnd-kit but leave the HTML5 cell handlers active, drag fires twice (once via HTML5, once via dnd-kit).
**Why it happens:** Reusing `SwimLane` without modifying it.
**How to avoid:** Add a `dragMode: 'native' | 'dnd-kit' | 'none'` prop. Default `'native'` preserves `/calendar`. Owner board passes `'dnd-kit'` and the SwimLane skips HTML5 wiring. Verify with a unit test that mounts `<SwimLane dragMode="dnd-kit">` and asserts no `onDrop` listener attached to cells.
**Warning sign:** Drop fires twice in network panel; chip moves then snaps back unpredictably.

### Pitfall 3: Server-side `agent_tasks` SELECT scope
**What goes wrong:** Owner-board fetches `agent_tasks` for entire team, including private profile data leaking via `assignment_reasoning.whyYouSentence`.
**Why it happens:** Owner sees ALL tasks in workload view, but `whyYouSentence` was Phase 3-bounded to "owner sees all, members see their own" (per CONTEXT.md).
**How to avoid:** The existing `/api/recgon/tasks/[id]` already strips `assignment_reasoning` to `whyYouSentence` per privacy filter. The owner-board MUST NOT bypass this — fetch chip detail via the existing endpoint on click, never include `assignment_reasoning` in the bulk dock+grid GET.
**Warning sign:** `whyYouSentence` showing for users it shouldn't, or raw JSONB in network response.

### Pitfall 4: Race between drag-drop optimistic update and dispatcher cron
**What goes wrong:** Owner drags task A from Mon → Thu. Mid-flight, the cron drain runs and the dispatcher re-evaluates A and reassigns it. Owner's API call lands and overrides cron's decision (or vice versa).
**Why it happens:** No locking; both surfaces write `agent_tasks`.
**How to avoid:** This is acceptable for v1 (last-write-wins per CONTEXT). Document explicitly. Long-term, consider an optimistic-concurrency-control row version, but out of scope for Phase 3.5.
**Warning sign:** "I just moved this task and Recgon moved it again" — surface as a known-limitation log line if it gets reported.

### Pitfall 5: `dnd-kit/core` vs `dnd-kit/react` import mistake
**What goes wrong:** Developer pastes `import { DragDropProvider } from '@dnd-kit/react'` from a 2026 blog post. That's the v2.0-pre-release API. Recgon installs `@dnd-kit/core@6.3.1` so the import fails or — worse — installs both packages and ends up with two parallel drag-drop systems.
**Why it happens:** dnd-kit's website shows BOTH APIs.
**How to avoid:** Lock the import path in CONVENTIONS or top of `OwnerWorkloadBoard.tsx`: `// dnd-kit STABLE v6 — import from @dnd-kit/core only. Do NOT import from @dnd-kit/react (v2.0-pre).`
**Warning sign:** `package.json` showing both `@dnd-kit/core` and `@dnd-kit/react`.

## Open Questions

### 1. Reschedule endpoint name + signature shape
**What we know:** D-16 mandates "POST /api/recgon/tasks/[id]/reschedule" but Claude's Discretion permits PATCH on `/route.ts` with `scheduled_date` in body. Existing `assign` route uses POST.
**What's unclear:** Should the new endpoint reuse `deferTaskScheduledDate()` directly, or introduce `ownerRescheduleTask()` to keep the dispatcher's "Deferred — qualified candidates booked" schedule_note copy distinct from owner-driven moves?
**Recommendation:** Add a new `ownerRescheduleTask(taskId, newDate | null, ownerId)` storage function that writes `schedule_note: 'Manually rescheduled by owner.'`. Keep dispatcher's `deferTaskScheduledDate` untouched so the audit trail honestly reflects WHO moved the task. Planner picks final naming.

### 2. Per-user dismiss persistence storage
**What we know:** D-17 says "Persists per-user (don't show again to that user)."
**What's unclear:** New table vs reuse of `agent_events`.
**Recommendation:** New table `owner_dock_dismissals(user_id UUID, task_id UUID, dismissed_at TIMESTAMPTZ, PRIMARY KEY (user_id, task_id))`. Add `DELETE` cascade on `agent_tasks(id)` so completed tasks don't leak rows. Planner confirms.

### 3. Capacity bar threshold tuning
**What we know:** D-07 says green/yellow/red derive from `match.ts` capacity numbers.
**What's unclear:** `SwimLane.tsx` already renders a per-day load bar with `dailyCap`-based overload detection (`overloaded = dayLoad > dailyCap`). Need a per-WEEK aggregation for the capacity bar described in D-07.
**Recommendation:** Add `weeklyCapacityHours(teammate)` helper alongside existing `dailyCapacityHours()` in `SwimLane.tsx`. Sum visible-week chip hours per teammate. Default thresholds: green < 60% utilization, yellow 60-85%, red > 85%. Planner picks final pixels.

### 4. Mid-drag dispatcher cron run
**What we know:** Multi-owner conflict resolution = last-write-wins per CONTEXT (v1).
**What's unclear:** Same applies to owner-vs-cron, but we should at least surface the risk in a code comment so future-us doesn't get confused.
**Recommendation:** No code change; add a comment in the reschedule endpoint noting cron + owner can race, last-write-wins.

### 5. Playwright install for keyboard a11y E2E
**What we know:** Manual UAT scenario D covers keyboard drag end-to-end. Vitest cannot fully simulate `KeyboardSensor` activation (needs real focus + key events on a layout-rendered DOM).
**What's unclear:** Whether to install Playwright for this phase or defer.
**Recommendation:** DEFER Playwright. The unit tests cover dispatch logic, and manual UAT signed off by user covers the experiential verification. Adding Playwright install + E2E config is a separate phase scope.
