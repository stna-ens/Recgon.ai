# Phase 3.5 Plan 01: Owner Task Board — Wave 1 Summary

Ships the owner-only entry point at `/projects` and the shared dnd-kit foundation. An owner navigating to `/projects` now lands on an empty workload board (14-day grid with one row per active teammate, DndContext mounted at root). A member or viewer still sees the existing project tiles list, byte-equivalent to the pre-refactor experience. `/calendar` and `/projects/[id]/tasks` are untouched — SwimLane's new `dragMode` prop defaults to `'native'`, so every existing caller keeps its HTML5 wiring.

## What changed

### Role-router refactor (Task 2)

Before: `src/app/projects/page.tsx` was 1,011 lines, ~25 hooks, all roles saw the same tile list.

After: `src/app/projects/page.tsx` is 35 lines, **1 hook (`useTeam`)**. Branches on `currentTeam.role === 'owner'` → `<OwnerWorkloadBoard teamId={...} />`; otherwise renders `<NonOwnerProjectsView />`. The original tile-list logic (~1,000 lines of hooks + JSX + styles) was moved **verbatim** into `src/components/v2/projects/owner/NonOwnerProjectsView.tsx`. The shell-regression test in `ownerBoard.shellRender.test.tsx` locks the stable structural markers (`.v2-projects-page`, `.v2-page-head`, `.v2-page-title` with `"$"` prompt, both CTAs) so an accidental refactor of NonOwnerProjectsView would fail in CI.

**Hook-order safety (Pitfall 1):** the new shell only calls `useTeam()` before the role branch — trivially safe under React Rules of Hooks. The prior hooks live inside `NonOwnerProjectsView`, where they always run unconditionally.

### OwnerWorkloadBoard shell (Task 2)

`src/app/projects/OwnerWorkloadBoard.tsx`:

- **Page chrome (UI-SPEC §4):** `PROJECTS` eyebrow in signature-pink JetBrains Mono, `Workload — {MMM D} → {MMM D}` headline (26px JetBrains Mono primary), year suffix, prev / today / next paging buttons.
- **14-day grid (D-06):** Builds 14 days starting from the Monday of the anchor week (week 1 = current week, week 2 = next). `<WeekHeader dayDates={14-elem} rowLabel="TEAMMATE" />` reused 1:1; new `<SwimLane>` per active teammate.
- **DndContext at grid root:** `useSensor(PointerSensor, { activationConstraint: { distance: 5 } })` + `useSensor(KeyboardSensor)`, `collisionDetection={closestCenter}`. `onDragEnd` is a no-op placeholder (wiring lands in 03.5-03 — flagged inline).
- **TriageDock placeholder:** Zero-height `<aside aria-label="Triage dock placeholder" />` — real dock arrives in 03.5-02.
- **Teammate fetch:** `/api/teams/${teamId}/teammates` (existing endpoint used by `/calendar`). Filter for `status === 'active'`. No new endpoint introduced.

### SwimLane `dragMode` extension (Task 1)

`src/components/v2/calendar/SwimLane.tsx` gained `dragMode?: 'native' | 'dnd-kit' | 'none'` (default `'native'`). The HTML5 wiring (`onDragOver` / `onDrop` / `onDragLeave` on cells, `draggable` on chips) now gates on `dragMode === 'native'`:

- `'native'` (default) — byte-identical to prior behavior. `/calendar` and `/projects/[id]/tasks` continue to work.
- `'dnd-kit'` — HTML5 listeners suppressed; cells still render so an outer `useDroppable` can attach refs.
- `'none'` — drag fully disabled.

The OwnerWorkloadBoard passes `dragMode="dnd-kit"` so chips (when they arrive in 03.5-02) participate in the page-level DndContext instead of competing with native HTML5 drag events. **RESEARCH § Pitfall 2** demanded this split — without it both systems would fire and create double drops.

### dnd-kit dependency lock

Pinned `@dnd-kit/core@^6.3.1` and `@dnd-kit/utilities@^3.2.2` (the stable v6 line). **Did not** install `@dnd-kit/react`, `@dnd-kit/dom`, `@dnd-kit/abstract`, or `@dnd-kit/sortable` (the v2-pre / sortable extensions — out of scope for positional drag). A file-header comment on `OwnerWorkloadBoard.tsx` documents this lock so future contributors don't accidentally import from the v2-pre package (Pitfall 5 hedge).

## Deviations from PLAN

**None functional.** Two minor planner-discretion choices worth flagging for downstream waves:

1. **`canReschedule={false}` on SwimLane in OwnerWorkloadBoard (Wave 1).** The PLAN said pass `cards={[]}` and `draggingTaskId={null}`; I additionally set `canReschedule={false}`. With no `onTaskDrop`/`onTaskResize` handlers yet, leaving `canReschedule=true` would attach drag-start handlers that have nowhere to land. Wave 03.5-03 will flip this to `true` when the reassign + reschedule endpoints exist.
2. **TriageDock placeholder is zero-height `<aside>` instead of an omitted slot.** Keeps the DOM tree shape stable so 03.5-02 can swap in the real component without touching OwnerWorkloadBoard's render tree.

The PLAN allowed planner discretion on tooltip / hover shape, optimistic-UI debounce, and several other details — none surfaced in Wave 1 (no chips, no interactions yet).

## Notes for Wave 2 (03.5-02 — Triage dock + chips)

1. **TriageDock anchor:** swap `<aside className="owner-board-dock-placeholder" />` for the real `<TriageDock />`. The placeholder sits between `<header className="owner-board-nav">` and `<DndContext>` — that's the contract.
2. **Chip data pathway:** the existing `/api/teams/[id]/calendar?projectId=...` endpoint is the analog WeekCalendar uses, but it scopes by `projectId`. For the owner board, we need an **all-projects** variant (e.g. `/api/teams/[id]/owner/board` returning `{ teammates, tasks }` across the whole team). Worth discussing in Wave 2 planning whether to extend `/calendar` to accept `projectId=*` or mint a new owner-only endpoint.
3. **`canReschedule` flip:** flip to `true` on SwimLane when the reschedule API ships in Wave 3 (not Wave 2). Wave 2 ships chips + dock but the reassign/reschedule endpoint + drag handler is Wave 3 work.
4. **SwimLane drop target:** currently `dragMode="dnd-kit"` suppresses HTML5 listeners. Wave 3 will wrap each day-cell in a `useDroppable` (via a thin wrapper component or a SwimLane prop, planner's call) — the cell `<div>` already renders with `data-day-index` + `data-teammate-id` so the droppable ref can attach.
5. **Multi-owner concurrency:** documented as "last-write-wins" in OwnerWorkloadBoard header comment. Wave 3 ships the mutations — the inline comment is just to anchor the deferred decision for future-us.
6. **Test scaffold usage:** the three exports in `setup.ts` (`assignedTask`, `triagedTask`, `deferredTask`) already match the three calendar/dock states Wave 2 needs. Reuse rather than re-fixture.
