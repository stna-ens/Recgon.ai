# Phase 03.5 Plan 03: Owner Task Board — Wave 3 Summary

The owner workload board is now fully actionable. Every dock row + every chip + every drag interaction reaches the same three endpoints (assign + schedule + dismiss) with the same optimistic-then-confirm pattern. The board is the owner's primary correction loop.

## Shipped

**Four inline action paths:**
1. **Triaged dock row → assign manually** — Radix DropdownMenu of active teammates → POST `/api/recgon/tasks/{id}/assign` with `{ assigneeId }` → optimistic remove from dock + toast `assigned to {name}`.
2. **Deferred dock row → dismiss ×** — POST `/api/recgon/owner/dock/dismiss` with `{ taskId }` → optimistic local hide + per-user persistence (other owners still see the row). No toast (silent dismissal per UI-SPEC §7).
3. **Chip in calendar → reschedule** — open `TaskDetailPanel` → click `reschedule` → Radix Popover with `<input type=date>` → POST `/api/teams/{teamId}/tasks/{taskId}/schedule` mirroring `WeekCalendar.handleTaskDrop` body shape exactly (`{ teammateId, scheduledDate, scheduledUntilDate }`). Toast `moved to MMM D`.
4. **Drag-drop** — four sub-modes:
   - **chip → lane label** (`{teammateId}__lane`): reassign keeping current date.
   - **chip → day cell** (`{teammateId}__{dateISO}`): reschedule keeping current assignee OR full reassign+reschedule when both change.
   - **dock row → day cell**: fires BOTH `/assign` + `/schedule` in one operation; row leaves dock + chip lands in cell + toast `assigned to {name} on MMM D`.
   - **drop outside any droppable** (over=null): no-op.

**In-flight ConfirmDialog (UI-SPEC §7):**
Reassigning a chip whose status is `accepted` or `in_progress` opens a Radix `AlertDialog` with copy "Reassign in-flight task?" + body explaining the consequence. Cancel → no fetch. Confirm → proceed with the drop. Destructive button styling.

**Endpoint reuse decisions (locked):**
- NO new endpoint for reschedule — REUSES existing `/api/teams/[id]/tasks/[taskId]/schedule` (already owner-gated at lines 24-26 of `route.ts`, verified during planning).
- NO new endpoint for manual-assign — REUSES existing `/api/recgon/tasks/[id]/assign` (Plan 03-07 owner-gated). The body field is `assigneeId` not `teammateId` — both new callers (picker + drag) use the correct shape.
- ONLY new endpoint: `POST /api/recgon/owner/dock/dismiss` (owner-only, 400 on triaged tasks, idempotent on duplicates).

**New migration: `20260517_owner_dock_dismissals.sql`**
- Table `owner_dock_dismissals(user_id TEXT, task_id UUID, dismissed_at TIMESTAMPTZ DEFAULT now())`.
- PK `(user_id, task_id)` — idempotency surface.
- Cascade FKs on both sides — cleanup is automatic when users or tasks are deleted.
- Index on `user_id` so `listDismissedTaskIds(userId, teamId)` filters quickly per-viewer.

**Storage layer:**
- `dismissDockItem(userId, taskId)` — idempotent upsert via Supabase `.upsert({ onConflict: 'user_id,task_id', ignoreDuplicates: true })`.
- `listDismissedTaskIds(userId, teamId)` — team-scoped via PostgREST inner join on `agent_tasks!inner(id, team_id)`.
- `listOwnerDockTasks(teamId, viewerUserId?)` — Plan 03.5-02 helper extended to optionally filter dismissed deferred rows for the given viewer. Triaged rows are NEVER filtered (D-17 hard rule).

**Optimistic state pattern (canonical Recgon):**
`OwnerWorkloadBoard` carries an `optimisticOverrides: Record<string, Partial<AgentTask>>` keyed by task id. On every mutation the override is applied immediately, the fetch fires, and on success `refreshAll()` re-pulls the server snapshot and the override clears. On failure the override is cleared and an error toast fires. Partial-failure path (assign succeeded, schedule failed) keeps the assign override + clears the date override + shows "reassigned but couldn't reschedule".

**dnd-kit wiring:**
- `OwnerWorkloadGrid` wraps each chip in `useDraggable({ id: task.id, data: { kind: 'task' } })`, each cell in `useDroppable({ id: '{teammateId}__{dateISO}' })`, each lane label in `useDroppable({ id: '{teammateId}__lane' })`. The three wrappers thread through SwimLane via three new optional props (`laneLabelWrapper`, `cellWrapper`, `chipWrapper`) with pass-through defaults so existing `/calendar` + `/projects/[id]/tasks` callers are byte-equivalent.
- `TriageDockRow` is itself a drag source via `useDraggable({ id: task.id, data: { kind: 'dock-row' } })`, with a small `⋮⋮` grip handle on the title-line. The inline assign picker + dismiss × stay clickable because the listeners are scoped to the grip element only.
- `OwnerWorkloadBoard.handleDragEnd` decodes the drop-target id via the exported `decodeDropTarget` helper, then routes to the in-flight ConfirmDialog if needed or directly to `performDrop`.

**Keyboard a11y:** dnd-kit's `KeyboardSensor` was mounted in Wave 1 and remains active. Tab to a chip → Space to grab → Arrow keys to move → Enter/Space to drop → Esc to cancel. dnd-kit handles screen-reader announcements out of the box; the same `handleDragEnd` fires for both pointer and keyboard.

## Deviations from Plan

### Rule 2 (correctness): drag-handle restricted to grip span on dock rows

**Found during:** Task 3 wiring.
**Plan said:** "Wrap the entire row in a useDraggable… Spread attributes + listeners onto the wrapper."
**Reality:** Spreading dnd-kit listeners onto the entire `<li>` made every interactive child (the dismiss × button, the AssignTeammatePicker trigger) inherit the grab cursor and absorb pointer events meant for the click handlers. Manual-assign + dismiss became unreachable.
**Resolution:** The drag-source ref stays on the `<li>` (`setNodeRef`), but `attributes` + `listeners` are bound to a small `⋮⋮` grip span at the row's title-line start. Click handlers on the dismiss × and the picker continue to fire normally. CSS `cursor: grab` is scoped to the grip only.

### Rule 3 (blocking): jsdom shim for Radix pointer-capture APIs

**Found during:** First test run of `ownerBoard.dockManualAssign.test.tsx`.
**Issue:** Radix DropdownMenu uses `Element.prototype.hasPointerCapture` / `setPointerCapture` / `releasePointerCapture` / `scrollIntoView` to manage focus. jsdom (vitest's default environment) doesn't implement these. The Radix trigger silently bailed on the missing APIs and the menu never opened, so `fireEvent.click(trigger)` did nothing.
**Fix:** Top-of-file shim that polyfills the four methods as no-ops if absent. Applied in `ownerBoard.dockManualAssign.test.tsx` and the three dnd integration test files. Also switched the test-side simulation from `fireEvent.click` alone to `pointerDown` + `pointerUp` + `click` for both the trigger and menu items — Radix opens menus on pointerdown, not click.
**Files:** `src/__tests__/ownerBoard.dockManualAssign.test.tsx` and three dnd files.

### Rule 1 (bug): visibleDeferred filter too strict

**Found during:** Wave-2 regression check after Task 2 wiring.
**Issue:** My initial `visibleDeferred` filter required `assignedTo === null && triageNote === null` on every deferred row. The Wave-2 invariant D-13 (`deferred appears in BOTH dock + calendar`) is exercised by the test 15 fixture using a soft-assignee on the deferred task — my filter dropped the row from the dock entirely, breaking `ownerBoard.workloadGridRender.test.tsx > Test 15`.
**Fix:** Drop the `assignedTo === null` predicate from `visibleDeferred`. The optimistic-clear-on-assign path is handled instead by checking the override directly (`optimisticOverrides[t.id]?.status === 'assigned' && optimisticOverrides[t.id]?.assignedTo`) — the row leaves the dock only when the owner has explicitly assigned it, not because of a soft-assigned seed.
**Files:** `src/app/projects/OwnerWorkloadBoard.tsx`.

### Rule 1 (bug): Wave-2 dockApi test asserted old single-arg signature

**Found during:** Full-suite check after Task 1.
**Issue:** `ownerBoard.dockApi.test.ts` asserted `expect(mockListOwnerDockTasks).toHaveBeenCalledWith('team-1')`. My Plan 03.5-03 change made the dock route pass `session.user.id` as a second argument.
**Fix:** Updated the assertion to `toHaveBeenCalledWith('team-1', 'user-owner')` with a comment pointing to the per-user-filter rationale.
**Files:** `src/__tests__/ownerBoard.dockApi.test.ts`.
