# Phase 3.5: Owner Task Board - Context

**Gathered:** 2026-05-15
**Status:** Ready for planning

<domain>
## Phase Boundary

The team owner opens **PROJECTS** in the top nav and lands on a single page that answers four questions at a glance:

1. **What needs my attention now?** — Triaged tasks the AI flagged (no clear fit, no grounded reason, no capacity, high-priority bypass) and deferred tasks (the AI pushed scheduling to a future date) sit in a pinned dock above the grid.
2. **Who has what on their plate?** — A Workload swim-lane grid (rows = teammates, columns = days, cells = task chips) shows every assigned task across all projects.
3. **Who is slammed and who is free?** — A capacity bar per teammate per week (green / yellow / red) shows utilization.
4. **What is this specific task, and why was this person picked?** — Click any chip to open the existing `TaskDetailPanel` with the Why-you sentence and metadata.

The owner can ACT directly on the page: manually assign triaged tasks, bump a chip's scheduled date via picker, dismiss a deferred item from the dock once reviewed, and drag-and-drop a task chip onto a different teammate (reassign) or a different day (reschedule).

**Personal `/tasks` page stays personal.** Members and viewers do NOT see the workload grid — PROJECTS for them keeps the existing project tiles. Owner is the only role that sees the board.

**Drilling into a single project** (clicking a project name/tile from anywhere) still routes to the existing per-project tasks list at `/projects/[id]/tasks` — that surface is unchanged in this phase.

</domain>

<decisions>
## Implementation Decisions

### Where the board lives
- **D-01:** PROJECTS landing IS the owner board. Owner clicks PROJECTS in top nav → sees the workload grid + triage dock. No new top-nav slot.
- **D-02:** Drilling into a specific project still shows that project's task list (existing `/projects/[id]/tasks` route — unchanged).
- **D-03:** Members and viewers see PROJECTS as the existing project tiles list (not the board). Server-side role check at the page level decides which view to render.
- **D-04:** The existing `/calendar` route stays the personal calendar view (unchanged). Team calendar lives at PROJECTS landing for owners only.

### Grid orientation (Workload swim-lane)
- **D-05:** Primary view = workload swim-lane: rows = teammates, columns = days. Reuses the existing `SwimLane` and `EventChip` components from `src/components/v2/calendar/` (don't rebuild from scratch).
- **D-06:** Default window width = **2 weeks** (this week + next). Owner pages forward/back to see beyond.
- **D-07:** Per-teammate-per-week capacity bar (green = healthy load, yellow = approaching cap, red = overloaded). Thresholds derive from the existing match.ts capacity numbers (the dispatcher already computes these).
- **D-08:** A secondary **Table view** toggle exists alongside Workload — same data, sortable rows by any column (priority, state, scheduled date). Workload is the default; Table is one click away for owners who need to sort.
- **D-09:** Industry analog: Asana Workload + ClickUp Team View + Monday Workload all converged on this shape. Recgon's twist: the AI mints + assigns, so the owner's role is triage + correction, not scheduling from scratch.

### Triage + deferred items
- **D-10:** Triage dock pinned ABOVE the workload grid, always visible (collapses to header chip when count = 0 to reduce noise).
- **D-11:** Dock style: **compact list rows**, one row per task. Format: `task title  ·  reason sentence  ·  [action button]`. Three to four rows visible without scrolling.
- **D-12:** **Triaged tasks** (`triage_note IS NOT NULL`, no scheduled_date or scheduled in the past) live ONLY in the dock. They have no calendar slot until assigned.
- **D-13:** **Deferred tasks** (qualified candidates exist but were booked, `scheduled_date` was moved forward by the dispatcher) appear in **BOTH** surfaces: in the dock as a "Needs Your Eyes" item AND in the calendar at their future date. Owner can dismiss from the dock with a single `x` click once they've reviewed — the chip stays in the calendar.
- **D-14:** Reason copy per triage_note (from Phase 3): `no_clear_fit` → "no clear fit", `no_grounded_reason` → "no grounded reason", `no_capacity_in_window` → "qualified but booked through 4 wks", `no_capacity_high_priority` → "high-priority + no capacity now", deferred → "deferred → {date}".

### Inline actions for v1
- **D-15:** **Manual assign** from triage dock: click "assign manually" → dropdown picker of active teammates → confirm → POSTs to existing `/api/recgon/tasks/[id]/assign` endpoint (shipped in Plan 03-07).
- **D-16:** **Bump scheduled date**: click any task chip → menu includes "reschedule" → date picker → on save, task chip moves in the grid. Server endpoint: a new `POST /api/recgon/tasks/[id]/reschedule` (owner-only, body: `{ scheduledDate }`).
- **D-17:** **Dismiss from dock**: tiny `x` button on each dock row — only available for deferred items (triaged items can't be dismissed; the owner has to act on them). Single click → row disappears from dock, task stays in calendar at deferred date. Persists per-user (don't show again to that user).
- **D-18:** **Drag-and-drop** is a v1 hard requirement (user explicitly insisted 2026-05-15):
   - Drag a task chip from teammate row A → drop on teammate row B = reassign (calls same endpoint as manual-assign with new teammateId)
   - Drag a task chip from day X → drop on day Y = reschedule (calls same endpoint as bump scheduled date with new scheduledDate)
   - Drag works in both directions; the drop target determines which action fires
   - Drag from the dock onto a calendar cell = both reassign (to the cell's teammate) + reschedule (to the cell's date) in one operation
- **D-19:** Drag-and-drop library: **`dnd-kit`** (lightweight, React 18+ compatible, accessible, no jQuery, used by serious projects). Don't roll our own.

### Claude's Discretion
- The exact pixel widths, typography sizes, exact color tones (sticking to `var(--signature)`, `glass-card`, `recgon-label` per existing design system).
- Loading skeletons, empty states (per Recgon's existing skeleton patterns).
- Server endpoint naming/shape (the new `POST /api/recgon/tasks/[id]/reschedule` is a planner choice; could also be `PATCH /api/recgon/tasks/[id]` with scheduled_date in body).
- Whether to debounce drag drops or commit immediately (planner picks based on optimistic-UI patterns).
- Tooltip / hover preview shape (when owner hovers a chip without clicking — show 1-line summary? full title?).

</decisions>

<specifics>
## Specific Ideas

### Industry analogs (named during discussion)
- **Asana Workload view** — gold standard for "rows = teammate, columns = time, cells = task chips, capacity bar per row." The new owner board is conceptually a Recgon-flavored version.
- **ClickUp Team View** + **Monday Workload** — same shape.
- **Linear Triage** — explicit queue for items needing routing. Recgon's dock is the same pattern, just AI-fed.

### What's specifically Recgon
- The AI mints + assigns autonomously. The owner's primary job is TRIAGE (act on AI refusals) + CORRECT (drag to override). Not schedule from scratch like in Asana.
- The deferral mechanism (Phase 3) produces "moved-by-AI" tasks that show up in the calendar AND the dock. Asana doesn't have this concept.
- Privacy filter on `whyYouSentence` carries through (owner sees all, members see their own).

### Drag-and-drop specifics (locked, user-emphasized)
- Drag a chip onto a different teammate row → reassign (POST `/api/recgon/tasks/[id]/assign`).
- Drag a chip onto a different day → reschedule (POST new `/api/recgon/tasks/[id]/reschedule` or PATCH `/api/recgon/tasks/[id]`).
- Drag from dock onto a calendar cell → both reassign and reschedule in one operation.
- Use `dnd-kit`. Don't roll our own.

</specifics>

<deferred>
## Deferred Ideas

- **`/tasks` redesign** — personal view still feels scrolly per UAT 2026-05-15. Belongs in its own phase. The Owner Task Board phase deliberately leaves `/tasks` alone.
- **Mobile-first interaction model** — workload grid doesn't fit phones; v1 falls back to a list of today's tasks + dock. A real mobile design is a separate phase.
- **Per-project filtering** — when owner is on the PROJECTS workload view, can they filter to "only show tasks from Project X"? Probably yes but not v1.
- **Multi-team support** — if the user owns multiple teams, do they switch teams via the existing team switcher? Yes (existing pattern), no new UI needed for v1.
- **Re-trigger dispatch on a single triaged task** — owner edits a teammate's profile, then says "try assigning this task again." Not v1; out of scope for now.
- **Re-mint task with edits** — owner edits task title/requiredSkills and re-runs assignment. Not v1.
- **Multi-owner conflict** — what if two owners drag the same task simultaneously? v1 = last-write-wins; conflict handling later.
- **Workload thresholds tuning** — capacity bar uses default green/yellow/red bands (e.g., <60% / 60-85% / >85%). Tuning these per-team is a settings feature, not v1.

</deferred>
