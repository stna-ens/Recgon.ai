## Phase Goal (plain English)

Hook the judge module into the real Recgon dispatcher. When two or three teammates are nearly tied on math, the dispatcher now stops, asks the judge once (per cron run, in a single batched call covering every close-call task), and uses the judge's pick. If the judge fails or the team has hit its daily safety cap, the dispatcher quietly falls back to the math top-1 — teammates never see a broken state.

<objective>
1. Restructure `runDispatch` into three passes (rank-all → batch-judge close-calls → assign+notify) per RESEARCH Q4.
2. Collapse `dispatchTask` to a degenerate N=1 case of the same pipeline (no duplicate code).
3. Add a per-team daily safety cap stored in a new `team_llm_usage` table — silent fallback when exhausted, single dev-ops email per team per day when the cap fires.
4. Add an in-process cache (single `Map` reset per cron run) keyed by `computeJudgeCacheKey` so retries inside one dispatch don't re-bill the LLM.
5. Lock the close-call threshold at **0.20** (RESEARCH Q1 sub-note recommendation; v3 quality > cost per CONTEXT D-30).
6. Ship integration test that proves the 3-pass restructure works end-to-end with a stubbed `chat`.

This plan does NOT yet write `assignment_reasoning` to the database — that needs the column migration which lives in Plan 03. For this plan, the dispatcher computes `reasoning` and PASSES IT through `dispatchSingleTaskWithReasoning`, but the storage layer just receives it as an unused arg (silently dropped). Plan 03 wires the actual write.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Cron-driven dispatcher → judge | Dispatcher initiates LLM calls on a schedule. Risk: runaway loop, cost exhaustion. |
| `judgmentBudget` ← multiple concurrent cron runs | Multiple Vercel cron instances could race on the counter. |
| `team_llm_usage` table writes | Cap counter is the SINGLE budget-enforcement surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02-01 | Denial of Service | Cron-driven judge calls | mitigate | Per-team daily cap (`DAILY_JUDGMENT_CALL_CAP = 50`) — silent math-fallback past the cap. Cap is a runaway-detection rail per CONTEXT D-30. |
| T-03-02-02 | Information Disclosure | Cap-exhaustion alert email | mitigate | Email fires AT MOST ONCE per `(team_id, usage_date)` via `cap_alert_sent` flag check-then-set. No team-specific data in the body beyond the team's UUID. Dev-ops address only (single env var, single recipient). |
| T-03-02-03 | Tampering | Concurrent counter increments | accept | RESEARCH Q4 note 2 — acceptable per-run margin for two cron instances racing the boundary. Cron is 1/minute, not 1/second; window is small. |
| T-03-02-04 | Elevation of Privilege | LLM picks a `chosen_candidate_id` whose math-rank index falls outside the math-prefiltered top-3 | mitigate | Schema literal `1|2|3` (Plan 01) PLUS dispatcher-side `index < entry.ranked.length` check (Plan 02 Task 4). Fallback to math top-1 if violated — QUAL-03 second-level enforcement. |
| T-03-02-05 | Repudiation | No audit trail of judge invocations | mitigate | `logger.info('judge_batch_invoked', ...)` on every LLM call; `logger.warn('judge_batch_failed', ...)` on error; cap events logged separately. Logs are searchable on Vercel. |
| T-03-02-06 | Tampering | Prompt injection via `task.title` reaching the LLM | mitigate | Tasks are minted by Recgon's own brain; titles are not user-typed freeform in the v3 pipeline. CONTEXT D-30 + Phase 1 D-13 precedent. If a future phase adds user-typed task titles, Plan-03's `buildJudgeTaskInput` must add `<user_content>` wrapping then. Comment-flagged in code. |
</threat_model>
