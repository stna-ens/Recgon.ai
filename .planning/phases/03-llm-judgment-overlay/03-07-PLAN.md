<objective>
**Gap surface for Plan 03-06 (gap_summary constraint 6):** "The dispatcher refusing to assign means tasks stay in `unassigned` state with a flag/note explaining why ('no teammate had a clear fit'). The owner needs to see unassigned ones with the triage hint. May need a small UI addition."

**Fix:** Surface triaged tasks in the TASKS page (`/tasks`) for owners with a dedicated tile + badge. Surface the triage state in TaskDetailPanel with an explanation block + owner-only 'Assign manually' CTA. Add the API endpoint that lets the owner override the refusal and assign a teammate manually (which clears the triage_note and writes a math_only AssignmentReasoning with whyYouSentence='Owner manually assigned').

**Purpose:** Plans 03-05 + 03-06 ensure Recgon REFUSES bad assignments. This plan ensures the owner can SEE and ACT on those refusals. Without this, a triaged task is invisible — the owner doesn't know Recgon punted on it.

**Output:**
- TASKS page triage column (owner-only).
- TaskDetailPanel TriageBlock (owner-only).
- Manual-assign API endpoint + Select picker integration.
- 2 new tests covering UI surface + manual-assign API.

**Why optional → why included now:** Without this, Plans 03-05/03-06 ship but produce silent refusals. The owner has no way to discover triaged tasks except by querying the database. Per gap_summary constraint 6 ("owner needs to see unassigned ones with the triage hint"), this surface IS required.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /api/recgon/tasks/[id]/assign | Untrusted POST body. Auth + role + payload validation server-side. |
| TaskDetailPanel client → owner role detection | Client-side hint only — the SERVER is the source of truth (the assign API re-checks role). Client-side hiding is UX, not security. |
| Triage column tile visibility | Same pattern: client-side hiding for UX; non-owners can technically GET /api/recgon/tasks and see triageNote (non-sensitive, so accepted). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3.1-07-01 | Elevation of privilege | Non-owner POSTs to /assign endpoint | mitigate | Server-side owner role check on the route — 403 on non-owner regardless of client-side UI. Test 2 in Task 1 covers this. |
| T-3.1-07-02 | Tampering | Manual-assign body specifies a non-team-member assigneeId | mitigate | Server validates assigneeId is a member of the task's team — 400 on invalid. Test 3 in Task 1. |
| T-3.1-07-03 | Repudiation | Manual-assign event not audited | mitigate | `logEvent({event: 'manually_assigned', payload: {owner_user_id, assignee_id, prior_triage_note}})` runs in the success path. |
| T-3.1-07-04 | Information disclosure | triage_note leaks to non-owner | accept | triage_note is metadata about WHY no assignment happened. Not PII, not skill data. Accepted per Plan 06's threat model. Members may see "no_clear_fit" in dev tools if they inspect API responses — fine. The UI hides it. |
| T-3.1-07-05 | DoS | Owner spams manual-assign | accept | Rate-limited by upstream Vercel + Supabase. Single owner per team; volume is small. |
| T-3.1-07-06 | Tampering | Race condition: owner manual-assigns while cron is in the middle of dispatching the same task | mitigate | `assignTask` already updates `status='assigned'` atomically; if cron lost the race, its second attempt sees status=assigned and skips. The triage_note clearing happens AFTER assignTask, both in a tight sequence — no observable inconsistent state. |
</threat_model>
